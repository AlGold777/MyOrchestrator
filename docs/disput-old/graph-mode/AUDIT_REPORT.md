# Graph Mode — аудиторский отчёт (задачи §7 брифа)

Дата: 2026-07-03. База: живое дерево 2.80.145 → 2.80.146. Бриф: `GRAPH_MODE_BRIEF.md` (рядом).
Статус: все четыре задачи §7 выполнены; найденные зацепления расцеплены (см. §1.3), тесты 99 suites / 550 green.

## 1. Аудит расцепления: транспорт vs Speaker/роли (§7.1)

### 1.1. Вердикт: фоновый слой чист

Диспетчер вкладок и весь background (`tab-manager.js`, `dispatch-coordinator.js`,
`job-orchestrator.js`, `message-router.js`, `human-presence.js`) **не содержат ни одного
упоминания** Speaker/ролей/очерёдности диспута. Единица работы фона — `(модель → вкладка →
промпт → ответ)`, состояние — per-model записи в `jobState.llms`. Граф-режим может строиться
на этом транспорте, ничего не «унаследовав» от диспута.

`runModelBatch` (results.js) — тоже чистый транспорт по сигнатуре: `prompt, models,
attachments, context, signal`. Вся логика ролей/очерёдности живёт в вызывающем коде диспута.

### 1.2. Найденные зацепления (оба устранены)

1. **Мёртвые импорты диспута в service worker.** `background/index.js` грузил
   `disput/disput-massage.js` и `disput/debate-engine.js`, при этом ни один
   background-модуль их не использует (потребители — только страницы `result_new.html` и
   `pipeline_panel.html`). Наследие удалённого «теневого executor'а». Убраны из
   `importScripts`; тест `release-log-regressions.test.js` теперь пришпиливает обратное:
   фон **не должен** грузить disput-модули.
2. **Вшитый LONG-профиль в `runModelBatch`.** Транспортная функция форсировала LONG
   generation-профиль с обоснованием «runModelBatch — диспетчер серийного диспута» — это
   допущение режима, зашитое в транспорт. Теперь `generationProfile` — параметр
   (`'long' | 'inherit'`, дефолт `'long'`, поведение диспута не изменилось); граф-операции
   смогут выбирать профиль per-operation (открытый вопрос брифа §10 про глубину среза —
   того же рода).

### 1.3. Что НЕ сделано сознательно (не блокер гейтов)

`runModelBatch` + `pipelineWaiter` живут внутри 19-тысячного замыкания `results.js`, а не в
общей библиотеке. Решение брифа «транспорт → общие библиотеки для обоих режимов» потребует
их извлечения в `shared/`. Это генеративная работа, по брифу она **гейтится Gate 0**:
до подтверждения ценности режима извлечение не окупается. Объём при извлечении: сам
`runModelBatch` (~90 строк), `pipelineWaiter` (results.js:2454), обработчики
final/partial-сообщений (results.js:~13830) и run-guard-ожидание.

## 2. Ревизия run-guard (§7.2)

### 2.1. Как устроено сейчас

- `shared/run-guard.js` — один boolean: `canStartNewRun()` отклоняет старт, если
  `session.roundsInProgress === true`. Диагноз брифа подтверждён: **ровно один batch за раз**.
- Глубже: у фона **один глобальный `jobState`** (`session` + `llms{model→entry}`), один
  промпт на batch (`runDispatchRounds(selectedLLMs, prompt)`), раунды 0–4 последовательны.
  Supervisor и human-presence тоже гейтятся на этот единственный флаг.

### 2.2. Рекомендация: semaphore-пул НЕ строить, волну выражать одним batch

Ключевой факт аудита: промпт течёт через оркестратор **per-model**
(`startModelForLLM(llmName, prompt)` — на каждом уровне раундов промпт передаётся в
вызов конкретной модели). Значит, поддержка карты `модель → промпт` в одном batch — дешёвое
локальное изменение (payload `START_FULLPAGE_PROCESS` + точки передачи prompt в раундах).

Следствие для графа: **волна из ≤3 операций = один batch с тремя парами (модель, промпт)**.
`concurrencyWidth` = размер волны-батча, run-guard остаётся односессионным без рефакторинга.
Автоснижение ширины при деградации — решение планировщика волн (сколько пар класть в batch),
а не свойство run-guard.

Альтернатива (пул конкурентных batch'ей + переделка `jobState` на per-run ключи) — на
порядок дороже: глобальный `jobState` вшит в orchestrator, coordinator, router, supervisor,
telemetry. Не делать без доказанной необходимости.

Ограничение подхода «волна = batch», зафиксировать в планировщике волн:
- одна модель не может исполнять две операции в одной волне (`jobState.llms` ключуется
  именем модели) — при пуле из 6+ моделей и ширине 3 это не ограничивает;
- волна ждёт самую медленную операцию (barrier semantics) — приемлемо для v1, где точка
  сжатия всё равно синхронная.

## 3. Gate 3 по существующим логам (§7.3)

### 3.1. Главный факт: прямых данных о JSON-валидности НЕТ

Расширение никогда не просило модели возвращать структурированный вывод: в коде нет ни
одного `JSON.parse` ответа модели (MODERATOR_ROUTE из Disput-3.1 в живом коде не парсится).
Ожидание брифа, что «Qwen confirmation failures / Grok recovery loops — те же данные под
другим тегом», не подтвердилось буквально: это события **транспортной** надёжности
(доставка/сбор ответа), а не дисциплины формата. Порог «≥70–75% schema-valid с первой
попытки» по логам измерить нельзя — только на ручном прогоне Gate 0
(`gate0/attack-wave-check.js` делает этот замер автоматически из сырых ответов).

### 3.2. Что логи дают: транспортная надёжность по моделям (прокси)

платформы):

| Claude | 103 | 9 | **8.7%** | ROUND2_REPAIR_CONFIRM_WAIT |
| GPT | 204 | 20 | **9.8%** | MANUAL_PING_FAIL |

### 3.3. Следствия для состава пула

- Транспортно-надёжное ядро для **структурных** операций (ATTACK/REPAIR/COMPRESS):
  GPT, Claude, DeepSeek (+ Perplexity — мало данных).
- Gemini, Qwen, Le Chat, Grok из пула **не выкидывать** (принцип покрытия, kill-condition
  «>25–30% находок не от топов»), но в v1 направлять их в первую волну (свободная форма,
  транспортные сбои волну не ломают — ответ просто не попадает в сжатие), а в структурные
  операции допускать по результату Gate 3-замера на ручном прогоне.
- Двойной риск Qwen/Gemini именно в структурных операциях: транспортный сбой и невалидный
  JSON неразличимы для оркестратора без ретрая — а ретрай ровно один (§4 брифа).

## 4. Комплект Gate 0 (§7.4) — `docs/graph-mode/gate0/`

| Файл | Что это |
|---|---|
| `node.schema.json` | JSON Schema узла по брифу §3: типы, статусы, рёбра с anchor-цитатой; `additionalProperties: false` — анонимность и traceability исполняются схемой. Поля «автор» нет. |
| `node-templates.json` | 10 готовых заготовок: все 5 типов × ключевые статусы (fresh/attacked/contested/stable/dead), пример D3-извлечения допущения с depends_on. |
| `prompts/decompose.md` | GENERATE = DECOMPOSE(topic); атомарность, типизация, извлечение допущений. |
| `prompts/attack.md` | Только атака, обязательный `anchor_quote`, структурированный отказ `solid`, съёмный блок синтетической провокации ({{BEST_DEFENSE}}, со 2-й волны). |
| `prompts/repair.md` | «Сильнейшая защита сначала» (R4), patch/concession/dispute_fact (A5), пометка сужения кванторов (R2). |
| `prompts/compress.md` | Кластеризация + защита выбросов (C2) + попарные расхождения (C3) + анти-противоречие в кластере (C1); каждый вход учитывается ровно один раз. |
| `attack-wave-check.js` | Скрипт двух замеров по волне: Gate 3 (чистый JSON с первой попытки / после извлечения / schema-valid, по слотам, включая A1-проверку anchor-цитаты) и доля дублей (Jaccard по словам и шинглам, порог брифа <20%). Без зависимостей, `node attack-wave-check.js wave.json`. |

Порядок ручного прогона Gate 0 — в `README.md` рядом.
