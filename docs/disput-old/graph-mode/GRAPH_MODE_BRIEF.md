# Graph Mode (Idea Reactor) — бриф для реализации

> Контекст: новый режим для LLM_Codex / расширения дебатов. Заменяет метафору «спор моделей»
> (Disput-3.1) на нагрузочное тестирование идеи как графа утверждений. Документ — консолидация
> решений из многомодельного анализа (2026-07-03). Disput-3.1 замораживается как есть.

## 1. Суть режима (минимум для понимания)

- Центральный объект — **граф утверждений**: узлы (claim / assumption / definition / mechanism /
  value_choice), рёбра (attack / support / refine / depends_on).
- **Нет спикеров, ролей, очерёдности.** Модель — stateless-исполнитель операции над срезом графа.
  В узле нет поля «автор» — анонимизация это отсутствие колонки в схеме.
- Цикл-насос: **расширение** (параллельные независимые операции, максимум энтропии) ↔
  **сжатие** (кластеризация, дедупликация, извлечение расхождений синтезатором).
- **Принцип изоляции первой волны (основа всей затеи, эмпирически проверен):** первичная генерация —
  строго независимые параллельные ответы, ни одна модель не видит чужих. Взаимодействие моделей до
  первого сжатия схлопывает разнообразие (якорение на чужих рамках). Атака/столкновение применяется
  только к расхождениям, извлечённым синтезатором из независимой волны; спорить о том, в чём модели
  сошлись независимо, — трата бюджета (независимое схождение = сильный сигнал).
- **Состав пула — по покрытию пространства, не по рангу моделей:** ценность источника — некоррелированность
  его взгляда, не средняя сила. Метрика: доля полезных находок синтезатора, пришедших не от топ-моделей.
  Если стабильно >25–30% — дешёвые/«странные» модели держатся в пуле принципиально;
  это kill-condition для интуиции «оставить только 3 сильнейшие».
- Выход: **ядро** (узлы, пережившие атаки), **карта разломов** (расхождения, пережившие ротацию
  исполнителей), **кладбище** (убитые узлы + какая атака убила).
- Человек — не модератор, а функция ценности: появляется только в точках сжатия,
  распределяет бюджет следующей волны (~2 минуты на решение).

## 2. Зафиксированные архитектурные решения (консенсус 8 моделей)

| Вопрос | Решение |
|---|---|
| Эволюция vs новый режим | Форкается только оркестрационный слой. Транспорт (вкладки, runModelBatch, pipelineWaiter, run-guard, парсинг, export) → общие библиотеки для обоих режимов. Route History / Instruction Burden / MODERATOR_ROUTE / serialDebateState — не переносятся. |
| Параллелизм | Ширина очереди 3 (реальный потолок вкладок 3–4). `concurrencyWidth` — runtime-параметр с автоснижением при деградации (рост латентности, ошибки парсинга, капча/редирект), не константа. |
| Хранилище (MV3) | IndexedDB: event log = отдельный object store с автоинкрементом (append-only), граф = снапшоты. Восстановление: последний снапшот + replay лога. chrome.storage.local — только настройки/указатели. File System Access — только экспорт (недоступен в service worker). Никакого состояния в памяти service worker. |
| MVP-операции | Ровно 4: `DECOMPOSE`, `ATTACK`, `REPAIR`, `COMPRESS`. GENERATE = DECOMPOSE(topic). RESOLVE = статус внутри COMPRESS, не операция. Новые операции — только при конкретной поломке, которая без них не объясняется (правило артефактов 2-го слоя). |
| Синтезатор (COMPRESS) | Фиксированный слот, дефолт Sonnet. На старте дублировать КАЖДОЕ сжатие второй моделью, пока не накопится 15–20 замеров расхождения кластеризаций; потом разредить до каждого N-го. Расхождение только логируется (паттерн densityScore). Порог для v2: стабильно >20–25% → двойной синтез. |
| Дедупликация атак | Отложена до замера на ручном прогоне. <20% дублей → не нужна в v1. Нужна → LLM внутри COMPRESS. transformers.js/эмбеддинги — только при измеренной поломке LLM-дедупа. |
| Событийная модель | Метрики (novelty, graph delta) считает оркестратор механически по дельте графа. Никаких самоотчётов LLM типа NO_SEMANTIC_DELTA. |

## 3. Схема узла (черновик)

```json
{
  "id": "n017",
  "type": "claim",
  "text": "…",
  "status": "contested",   // fresh | attacked | repaired | stable | dead | contested
  "edges_in": [{"kind": "attack", "from": "n031", "born_wave": 3, "survived_rotation": true}],
  "load_cycles": 2,
  "origin_cluster": "c04"
}
```
Каждое ребро хранит anchor-цитату источника (turnId + 1–2 предложения) — недоказуемые дельты
оркестратор не применяет (перенос принципа traceability из Disput-3.1).

## 4. Промпт-принципы операций

- ATTACK: «Если уязвимостей нет — верни структурированный отказ `{"status":"solid","reason":"…"}`»
  (не пустой ответ — парсится надёжнее). Не предлагать альтернативу, только атака.
- REPAIR: «либо patch, либо concession» — запрет на вежливую капитуляцию.
- Сборщик контекста подаёт операции только узел + соседей 1-го порядка, только поля text/type.
  Изоляция — свойство сборщика (код), не дисциплина промпта.
- Ротация: узел не атакуется тем же слотом модели две волны подряд
  (хранить `(node_id, last_attacker_slot)`). Обоснование — декорреляция слепых пятен, не «честность».
- **Синтетическая провокация** (компенсация потерянной генеративности живого спора): начиная со 2-й
  волны ATTACK получает не голый узел, а узел + его лучшую существующую защиту (анонимный текст) с
  инструкцией «найди слабейшее место с учётом того, что утверждение уже защищено так». Столкновение
  воспроизводится как операция, без спикеров.
- **Деградация при невалидном выводе** (перенос из Disput-3.1): невалидный JSON → 1 ретрай с
  промптом-коррекцией → повторный провал → дельта отбрасывается целиком и логируется, частичное
  применение запрещено. Ретрай во вкладочной среде дорог — поэтому ровно один.

## 5. Численные триггеры (v1, до калибровки)

```
новых кластеров в волне < 15%        → расширение остановлено, переход к сжатию
узел contested после 2 циклов        → пометить fault_line
изменено рёбер за полный цикл < 5%   → сессия завершена (равновесие)
после 1-го сжатия ≤ 2 кластера       → kill: переформулировать вход
```
Пороги временные (постулированные). План на потом: канареечная калибровка — три засеянных узла
(тривиальность / заведомо опровержимое / неразрешимый ценностный спор), пороги = «неотличимо от
канарейки данного типа». В v1 не делать, дорого; включать только на финальных проходах.

## 6. Порядок работ — гейты (ничего не строить до прохождения)

**Gate 0 — ручной прогон (без кода, руками).** 1 идея → 6–10 независимых ответов моделей →
COMPRESS через Sonnet → 10–15 узлов вручную в JSON → волна ATTACK → REPAIR → карта разломов.
Протокол слепой: карту разломов выписать, НЕ глядя в исходные ответы, сверить потом.
Критерий: ≥1 расхождение, невидимое в исходных независимых ответах.
Провал → одна итерация оптимизации промптов ATTACK/COMPRESS → повторный провал → оркестратор не пишется.

**Gate 1 — замер параллелизма.** 2/3/4/5/6 вкладок: латентность, доля сбоев, память,
троттлинг, блокировки провайдеров. Выход: рабочий `concurrencyWidth`.

**Gate 2 — замер сброса контекста.** Кандидат №1: программный DOM-клик по «New Chat» внутри
открытой SPA (чистый контекст без перезагрузки/ре-инициализации). Проверить на 3 целевых сервисах.
Запасной: пул чатов со сбросом раз в M операций; M калибруется канареечным тестом
(факт в «игнорируемой» части → доля всплытия; порог ~5–10%).

**Gate 3 — JSON-валидность по моделям.** СНАЧАЛА перечитать существующие логи LLM_Codex
(Qwen confirmation failures, Grok recovery loops — это те же данные под другим тегом).
Порог пула структурных операций: ≥70–75% schema-valid с первой попытки. Все «известные» проценты
по моделям из внешних источников — выдумка, доверять только своим замерам.

**Gate 4 — парный тест честности атак.** Двусторонний, односторонний пропускает ленивые модели:
(а) на крепких канареечных узлах ≥70–80% отказов `solid`; (б) на заведомо уязвимых узлах — низкая
доля отказов. В пул атакующих — только модели, прошедшие ОБЕ стороны. Нюанс разметки: мета-атака
на тавтологию («верно только в десятичной системе») — легитимна, не мусор.

**Только после Gate 0–4 → писать DAG-планировщик.**

## 7. Первые задачи для Code (аудиторские, не генеративные)

1. Проверить расцепление: знает ли диспетчер вкладок / runModelBatch про Speaker/роли.
   Если да — расцепить ДО любой работы над граф-режимом, иначе граф унаследует допущения очерёдности.
2. Ревизия run-guard: `roundsInProgress` рассчитан на один batch → нужен semaphore-пул с лимитом = concurrencyWidth.
3. Перечитать логи под Gate 3 (JSON-валидность по моделям).
4. Подготовить для Gate 0: JSON-шаблоны узлов, промпт-шаблоны 4 операций, скрипт подсчёта дублей в волне атак.

## 8. Экран оператора (точка сжатия) — спека UI

Не граф. Дельта-ориентированный дашборд:
- **Что изменилось с прошлого сжатия** (diff, не полный срез).
- Contested-узлы по убыванию циклов; у каждого: вектор атаки одной строкой
  («нет источника» / «подмена термина» / «скрытое допущение») + anchor-цитата + счётчик циклов (proxy уверенности).
- Кандидаты в stable (+ сколько и каких типов атак отражено) + кнопка ручной заморозки узла.
- Кладбище с тегом FailureReason (для паттернов ошибок).
- Предложение бюджета: узел → why this node → операция → стоимость в вызовах → novelty-прогноз.
Цель: решение о бюджете за ~2 минуты.

## 9. Отклонённые альтернативы (не поднимать без нового аргумента)

- Полная декомпозиция ролей / отдельные вызовы на подзадачи анализа — latency/cost, план v2.
- Адаптивная частота по плотности — требует пред-парсинга, ломает pipeline; логируем densityScore.
- transformers.js для дедупа в v1 — вес/CPU ради задачи неизвестного объёма.
- «Игнорируй всё выше» как основной механизм амнезии — утечка контекста, проверено ненадёжно;
  допустим только как fallback с канареечным контролем.
- Теневой лог «исполнитель как латентная переменная» для калибровки моделей — окупается на сотнях
  сессий; в v1 просто писать model-slot в events, не использовать.

## 10. Открытые вопросы (не блокеры v1)

- Семантический дрейф узла после N ремонтов: «выжил» vs «заменён» — нужна метрика и порог.
- Глубина среза контекста для ATTACK: параметр типа операции, а не константа системы?
- Декорреляция атак пула: как дёшево измерить на узлах с заранее известными уязвимостями.
- Веса от человека: какие собирать до сессии, какие — только после первого сжатия (риск якорения планировщика).

## 11. Каталог корректирующих запросов (закрытый, v1)

Принципы: (1) триггер обнаружим механически или синтезатором — самоотчёту исправляемой модели не верим;
(2) коррекция — обычная stateless-операция с минимальным срезом, без истории «ты ошибся»;
(3) loop-guard: одна коррекция × один объект × максимум 1 применение; повторный триггер → эскалация
человеку, третьей попытки нет. Новые записи — только по правилу артефактов 2-го слоя.

### DECOMPOSE
| ID | Триггер (детектор) | Корректирующий запрос |
|---|---|---|
| D1 SPLIT_COMPOUND | узел содержит несколько утверждений (синтезатор, 1-е сжатие) | «Расщепи на атомарные утверждения, каждое атакуемо отдельно» |
| D2 RETYPE | ≥2 атак вида «это не факт, а выбор/допущение» (механика по типам рёбер) | переклассификация узла + перенос рёбер |
| D3 EXTRACT_HIDDEN_ASSUMPTION | ≥2 атак на разные узлы с общим корнем (синтезатор) | «Извлеки допущение в отдельный узел, привяжи зависимые» |

### ATTACK
| ID | Триггер | Корректирующий запрос |
|---|---|---|
| A1 ANTI_STRAWMAN | anchor-цитата не найдена в тексте узла (валидатор, механика) | «Атакуй буквальный текст узла, процитируй атакуемый фрагмент» |
| A2 VARY_ATTACK_TYPE | семантический дубль существующего ребра (дедуп) | «Слабость типа X уже найдена; ищи тип "логика"/"граница применимости"/"контекст"» |
| A3 PROVOKE | slot вернул solid на узле, успешно атакованном другим слотом в той же волне | синтетическая провокация: узел + лучшая защита + «что эта защита не закрывает» |
| A4 ATTACK_ONLY | вместо атаки — альтернативное решение (схема-валидатор) | «Только уязвимости, без встречных предложений» |
| A5 SOURCE_OR_RETRACT | REPAIR оспорил фактическую базу атаки (поле dispute_fact) | атака в карантин; автору: «Подтверди источник или отзови». Нет подтверждения → dead, тег hallucinated |

### REPAIR
| ID | Триггер | Корректирующий запрос |
|---|---|---|
| R1 SUBSTANTIVE_OR_CONCEDE | семантическая дельта ≈ 0 при незакрытой атаке (синтезатор) | «Ремонт не отвечает на атаку […]. Либо содержательный patch, либо явный concession» |
| R2 MARK_SCOPE_NARROWING | кванторы сужены без пометки (синтезатор, до/после) | «Сужение области = concession со сменой формулировки; оформи явно» |
| R3 THESEUS_CHECK | ≥3 ремонта узла (счётчик) | другому слоту: «исходная vs текущая формулировка — то же утверждение?»; «другое» → исходный в кладбище (replaced), новый узел, load_cycles=0 |
| R4 STRONGEST_DEFENSE_FIRST | concession на атаку, отбитую другим слотом/узлом (сравнение по волне) | «Сформулируй сильнейшую защиту; сдавайся, только если она не работает» (анти-RLHF-капитуляция) |

### COMPRESS
| ID | Триггер | Корректирующий запрос |
|---|---|---|
| C1 SPLIT_CLUSTER | attack-рёбра между членами кластера (механика) | «Кластер содержит противоречие, разбей» |
| C2 PRESERVE_OUTLIER | вход не покрыт кластеризацией / единичный ответ слит (механика: счёт входов) | «Перечисли невошедшие ответы; единичные выделить, не сливать» — защита странных углов зрения |
| C3 PAIRWISE_COMPAT | расхождение нашёл второй синтезатор, но не первый (период дублирования) | «Для каждой пары кластеров: совместимы или противоречат, в чём» |

### Планировщик / сессия (без LLM)
| ID | Триггер | Действие |
|---|---|---|
| S1 FORCE_LOAD | 0 атак на узел за 2 волны (аудит-лог планировщика) | принудительная атака; stable без минимальной нагрузки не присваивается |
| S2 FREEZE_SINK | узел съел >20% бюджета без смены статуса | заморозка + эскалация человеку на ближайшем сжатии |
| S3 EQUILIBRIUM_GUARD | критерий <5% сработал при наличии недогруженных узлов | равновесие не засчитывается; бюджет принудительно на недогруженные |

Примечание: почти весь каталог диагностирует болезни артефакта/исполнителей, а не разговора —
болезни разговора (дрейф, ложный консенсус, повторы из каталога C Disput-3.1) умерли вместе с
разговором. Единственная наследница — R4: вежливая капитуляция живёт в RLHF моделей и переживает
любую архитектуру.
