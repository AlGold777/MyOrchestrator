Профиль Disput: полное описание конфигурации (итоговая редакция)

Профиль — декларативное описание регламента спора. Перед запуском он компилируется в неизменяемый план исполнения; все правила из профиля проверяются движком по состоянию дела, а не по заявлениям моделей. Настройка, которую движок не может проверить программно, в профиле не существует — она может быть только формулировкой в инструкции модели, без гарантий исполнения.

Первичный продукт спора — карта состояния (п. 7): структурированная картина проблемы, детерминированно выводимая из дела на любом этапе. Итоговый вердикт — одна из проекций карты, а не её замена. Цель протокола — не принудить участников к согласию, а построить максимально полную и честную карту: где позиции сходятся, где расходятся непримиримо, что доказано и чего не хватает. Вся дисциплина закрытия возражений (пп. 5–6) служит именно этому: особое мнение ценно ровно потому, что выжило под машинерией закрытия, — несогласие, которое никто не пытался разрешить, было бы шумом, а не информацией.

1. Паспорт и версионирование

Параметры: идентификатор, версия (semver), статус, тип задачи, родительский профиль.

  • Статусы: draft — в разработке, validated — прошёл приёмочные прогоны, deprecated — запрещён для новых запусков.
  • Статус validated присваивается связке: версия профиля + хеш пакета инструкций + версия схем данных + совместимый диапазон версий движка. Технический патч движка статус не сбрасывает; изменение значимого поведения — сбрасывает в draft. Изменение профиля, инструкций или схем сбрасывает статус всегда.
  • Критерий приёмочных прогонов — качество карты, а не доля исходов. Оценивается: покрытие осей вердиктами, сохранность особых мнений, обоснованность закрытий. Доля resolved метрикой качества не является: partial с двумя критиками и честным dissent информативнее, чем resolved с одним критиком, не нашедшим проблем. Настройка профиля, повышающая долю resolved за счёт ослабления стандарта закрытия, сужения окна стагнации или сокращения критиков, — регресс, а не улучшение.
  • Наследование — один уровень. Скалярные значения — замена; массивы с идентификаторами — слияние по id; удаление элемента родителя — пометка _remove.

Предмет обсуждения: базовый профиль-родитель; состав приёмочных прогонов.

2. Онтология: словарь спора

Единый словарь, на который ссылаются все остальные блоки.

  • Типы утверждений (claim_types): например, факт / гипотеза / оценочное суждение. Тип определяет требования доказательности, в том числе минимальный ранг доказательства для закрытия возражения (для факта — source_verified, для оценочного суждения может быть достаточно model_argument). Соответствие «тип → минимальный ранг» задаётся здесь и проверяется движком при закрытии.
  • Для доменов со структурированной аргументацией рекомендуются типы assumption / value_premise (предпосылка / ценностная посылка): размеченные предпосылки позволяют карте показывать, что два непримиримых вывода упираются в одну расходящуюся посылку, — это и есть настоящий предмет разногласия. Отдельный механизм не нужен: предпосылки — обычные утверждения со статусами и ссылками.
  • Ранги доказательств (evidence_tiers): упорядоченный список, например source_verified > model_argument.
  • Оси критики (critique_axes): id, формулировка вопроса, флаг required, флаг blocking (открытая проблема по оси блокирует исход resolved).

Критерий покрытия оси — существование артефакта «вердикт по оси»: issue_found / no_issue / not_applicable + перечень проверенных утверждений. Произвольная запись с нужным axis_id покрытием не считается.

Предмет обсуждения: состав осей — операциональное определение качества домена; флаги required/blocking; таблица минимальных рангов.

3. Роли

Профиль фиксирует роли и ограничения; привязка моделей происходит при запуске и в профиль не входит.

  • Кардинальность: min/max экземпляров на роль.
  • Запрет совмещения (exclusive_with): арбитр ≠ автор, синтезатор ≠ участник дискуссии. Проверяется до старта; нарушение — отказ в запуске.
  • Требования к возможностям (поиск, длинный контекст) — на уровне стадии, не роли.
  • Слияние при кардинальности > 1, по типу артефакта:
    • Возражения: группировка по ключу «целевое утверждение + ось»; записи с одним ключом, но разным содержанием сохраняются как отдельные внутри группы; конфликт серьёзности — в пользу максимальной.
    • Вердикты по оси: совпадающие сливаются; конфликт вердиктов (issue_found против no_issue) не разрешается автоматически, а фиксируется как запись особого мнения (п. 5.1) и передаётся арбитру. Расхождение критиков — не ошибка слияния, а материал карты.
    • Отсутствие политики слияния у стадии с множественной ролью — ошибка компиляции.

Предмет обсуждения: число критиков (стоимость против плотности карты); матрица запретов совмещения.

4. Граф стадий

Маршрут спора — конечный автомат (workflow-граф): обратные переходы (циклы «критика → ответ → критика») разрешены и ограничены потолком раундов из п. 6. Стадия задаёт: роль, обязательные входы, контракт выходных артефактов (п. 5), режим приёмки, таймаут, условия перехода.

  • Условия переходов — типизированные предикаты из закрытого каталога движка («поле, оператор, значение»). Произвольные выражения не допускаются. Первое истинное сверху вниз. Параметры предикатов валидируются против онтологии при компиляции.
  • Приоритет уровней управления: бюджет → потолок раундов → глобальные условия остановки → переходы графа.
  • Режим приёмки — partial или atomic. Невалидный выход: одна повторная отправка с перечнем ошибок валидации; при повторном нарушении — для partial-стадий допустим salvage (детерминированное извлечение валидных элементов массивного выхода, режим degraded, запись в лог); для atomic-стадий (синтез, решение арбитра) — только abort_run или деградированный исход спора.
  • Недоступность исполнителя (on_dropout): optional-стадии — пропуск; обязательные — переназначение или остановка. Таймаут стадии — случай on_dropout, не невалидного вывода.
  • Таймаут — индивидуальный на стадию.

Предмет обсуждения: состав стадий домена (перекрёстный допрос, проверка фактов, верификация синтеза — опциональные стадии); режимы atomic/partial; политика при сбоях.

5. Артефакты: всё, из чего состоит дело

Всё порождаемое в споре — типизированные артефакты: записи с фиксированной схемой, обязательными полями, взаимными ссылками. Совокупность артефактов — «дело»; по нему вычисляется любое правило движка и из него же детерминированно выводится карта состояния (п. 7). Артефакт, не попавший в дело, для системы не существует — в том числе для карты.

5.1. Типы артефактов

  • Утверждение (claim). Единица позиции: текст, тип из онтологии, статус. Конечный автомат:

    Переход Актор Требование
    asserted → contested движок появилось открытое возражение
    contested → asserted движок все возражения закрыты/отозваны
    contested → refuted арбитр обоснование + ссылка на возражение с доказательством
    asserted/contested → confirmed арбитр доказательство ранга не ниже минимального для типа

  • Доказательство (evidence). Ранг из онтологии, содержимое или ссылка на источник, происхождение.

  • Возражение (ledger entry). Текст, ссылка на утверждение, ось, серьёзность, ссылка на доказательство, статус (п. 5.3).

  • Вердикт по оси (axis verdict). Итог проверки оси с перечнем проверенных утверждений.

  • Особое мнение (dissent record). Порождается движком при неразрешённом конфликте: расходящиеся вердикты по одной оси, решение арбитра вопреки зафиксированной позиции участника. Типизированный источник секции dissent карты — движок выводит записи, а не интерпретирует текст.

  • Предложение о закрытии (closure proposal). Ссылка на возражение + ссылка на доказательство; вход для решения арбитра.

  • Карта состояния / итоговый отчёт. Проекции дела с фиксированной схемой (п. 7).

5.2. Общие правила

  1. Контракт стадии: какие типы артефактов потребляет и обязана произвести. Ответ без обязательных артефактов невалиден (последствия — п. 4).
  2. Ссылочная целостность сквозная. Ссылка на несуществующий объект = невалидный вывод. Локальные идентификаторы: артефакты, создаваемые в одном ответе со ссылками друг на друга, используют временные ID (evidence_1); движок транслирует их в постоянные при коммите; валидация — после трансляции.
  3. Происхождение (provenance): кто (роль, модель), на какой стадии, в каком раунде. Для любой строки карты восстановима цепочка «какое возражение → каким доказательством → чьим решением».

5.3. Жизненный цикл возражения

Переход Актор Требование
open → closed арбитр доказательство ранга не ниже минимального для типа утверждения + письменное основание
open → accepted_as_limitation арбитр структурированное обоснование {причина, влияние на выводы, возможная компенсация}
open → withdrawn критик —

Автор предлагает закрытие, движок проверяет целостность, ранг и допустимость перехода, арбитр решает по существу. Переходы вне таблицы отклоняются.

accepted_as_limitation — для обоснованных возражений, неустранимых в рамках спора. Для остановки не считается открытым; в карте выводится в разделе ограничений принудительно. Влияние на исход: ограничение по blocking-оси ограничивает максимальный исход до partial.

5.4. Снимок дела (snapshot)

Вход стадии — проекция дела для моделей (не путать с картой состояния — проекцией для пользователя; обе выводятся из одного дела, но служат разным читателям). Движок отбирает, какие артефакты видит роль на стадии. Защищённые сущности: открытые возражения, перечень утверждений и индекс поднятых ключей «утверждение + ось» не вытесняются ни на одной ступени переполнения (п. 6) — иначе после сжатия контекста модель повторяет рассмотренное, дедуп гасит повторы и спор завершается ложной стагнацией.

Предмет обсуждения: доменные типы и поля; таблица минимальных рангов. Расширение типов — легально; ослабление ссылочной целостности — нет.

6. Управление: остановка и бюджеты

Все условия вычисляются движком по делу. Самоотчёт моделей сигналом не является.

  • Раунды: min/max — жёсткие границы циклов.
  • Успешное завершение: нет открытых блокирующих возражений И полнота вердиктов по обязательным осям.
  • Стагнация: окно в N раундов с нулём по трём сигналам: новые уникальные записи (ключ «утверждение + ось»; грубость ключа осознанна — ошибка в консервативную сторону), переходы статусов, новые доказательства. Те же три сигнала образуют секцию «Динамика» карты (п. 7): пользователь видит ровно то, по чему движок судит о прогрессе.
  • Бюджет раздельный: лимит входа + зарезервированный лимит генерации. Резерв на завершение: бюджет терминальных стадий откладывается при старте; новый раунд не начинается, если остаток без резерва исчерпан. Заметим: даже при аварийной остановке карта состояния доступна всегда — её экспорт не требует моделей и бюджета (п. 7); резерв защищает прозаический синтез, а не карту.
  • Переполнение контекста: 80% — детерминированный отбор; 90% — структурное уплотнение; 95% — экстрактивное сжатие. LLM-суммаризация в стандартной цепочке отсутствует. Защищённые сущности (п. 5.4) не вытесняются.
  • Квота записей за ход (max_objections_per_turn).

Предмет обсуждения: потолки; резерв на завершение; окно стагнации; квота.

7. Карта состояния и итоговый отчёт

Карта состояния — первичный продукт спора: структурированная картина проблемы, какой её установил спор к данному моменту. Она существует непрерывно с первого раунда и полноценна на любом этапе: спор, остановленный по бюджету или стагнации, не «провалился» — его результат есть карта на момент остановки.

7.1. Принцип формирования

Карта — детерминированная проекция дела: каждая секция — выборка типизированных артефактов по фиксированному правилу. Модели в сборке не участвуют. Следствия: карту нельзя приукрасить (ни синтезатор, ни кто-либо ещё не может пропустить неудобное возражение — секции собирает код); карта воспроизводима (одно дело — одна карта); каждая строка прослеживаема через provenance.

7.2. Состав секций и их деривация

Секция Из чего выводится
Позиции и утверждения все claims со статусами, сгруппированы по владельцу
Состояние проверки вердикты по каждой обязательной оси; непокрытые оси показаны явно
Открытые возражения записи open, с осью, серьёзностью, флагом blocking
Закрытые возражения записи closed: чем закрыто (доказательство, ранг) и чьим решением
Особые мнения dissent-записи (п. 5.1)
Принятые ограничения accepted_as_limitation с обоснованиями {причина, влияние, компенсация}
Дефицит доказательств утверждения-факты без доказательства минимального ранга
Доказательная база все evidence с рангами и происхождением
Динамика изменения за последний раунд — сигналы стагнации из п. 6

Состав фиксирован архитектурно: профиль может добавлять доменные секции, сокращать — нет.

7.3. Два режима экспорта

  • Промежуточная карта — после любого раунда, по запросу или автоматически. Только движковые секции, без прозы и терминального исхода. Стоимость — ноль обращений к моделям.
  • Финальная карта (итоговый отчёт) — те же движковые секции плюс проза синтезатора (резюме, консенсусные и спорные утверждения, доменные разделы) плюс терминальный исход.

Инвариант: движковые секции финальной карты идентичны промежуточному экспорту на тот же момент. Проза добавляется рядом с картой, а не вместо неё; синтез — проекция карты, не её замена. Синтезатор — участник с ролью и контрактом (atomic, п. 4), его выход не может модифицировать движковые секции.

7.4. Терминальные исходы

resolved / partial / inconclusive / budget_limit / stagnation. inconclusive — легитимный исход: честная фиксация того, что вопрос не решается имеющимися данными, — информация, а не сбой. resolved недостижим при блокирующих ограничениях (п. 5.3) — движок понижает исход до partial автоматически.

7.5. Чем карта не является

  • Не заменой дисциплины закрытия. Ценность dissent в том, что он выжил: возражение пытались закрыть, арбитр проверял релевантность — и оно устояло. Рамка «карта важнее вердикта» не ослабляет ни стандарт закрытия, ни требование полноты вердиктов.
  • Не логом переписки. Реплики моделей в карту не входят — только артефакты со статусами; текст доступен через provenance.
  • Не метрикой согласия. Качество карты — плотность покрытия и обоснованность закрытий, не доля resolved (критерий приёмки — п. 1).

Предмет обсуждения: состав доменных прозаических секций и доменных секций карты. Состав и деривация базовых движковых секций обсуждению не подлежат — это архитектурная гарантия.

8. Пакет инструкций (prompt pack)

Инструкции для каждой пары «стадия × роль» — build-артефакт компиляции профиля: собираются детерминированно из блоков 2–6 и шаблонов-источников; контент-хеш входит в fingerprint валидации (п. 1). Ручные правки — только через шаблоны-источники и пересборку.

Сериализация: формат выдачи артефактов (строгий JSON, маркированный текст) — свойство пакета инструкций и парсера, выбирается по способу подключения модели (API / чат через DOM). Типизация, ссылочная целостность и контракты стадий от формата не зависят.

9. Гарантии исполнения

  1. Проверка при компиляции. До первого обращения к моделям: наличие инструкции для каждой пары «стадия × роль»; принадлежность предикатов каталогу и валидность их параметров против онтологии; ссылочная корректность схем; политики слияния у множественных ролей (отдельно для возражений и вердиктов); отсутствие пропуска обязательных стадий; корректность режимов atomic/partial; покрытие переходов статусов (возражений и утверждений) таблицами полномочий; достаточность бюджета с учётом резерва на завершение. Нарушение — отказ в запуске.
  2. Снимок конфигурации. Разрешённая конфигурация фиксируется при старте и неизменна до завершения. Редактирование профиля не влияет на идущие споры; для завершённого спора восстановимы точные правила.
  3. Карта — всегда. Экспорт карты состояния возможен в любой момент жизни спора и после его завершения, детерминированно и без обращений к моделям. Ни один сценарий отказа (бюджет, стагнация, dropout, abort_run) не оставляет пользователя без карты на момент остановки.
  4. Граница гарантий. Гарантируются воспроизводимость конфигурации, воспроизводимость карты из дела, трассируемость шагов и реплей плана. Идентичность ответов моделей при повторном запуске не гарантируется — это свойство исполнителей, а не регламента.
