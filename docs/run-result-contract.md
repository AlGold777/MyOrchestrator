# Контракт результата run: типизированный результат, лестница доказательств, транспорт

Введено на версиях **2.81.311–2.81.317**. Реализует раздел 1 разбора
«Формализация задачи и контракта результата» и те части разделов 3–5, без
которых он не работает.

Действующая архитектура извлечения ответа описана в
`answer-completeness-handoff.md`; каталог отложенных альтернатив — в
`answers-detection-alternativa.md`. Настоящий документ описывает слой, который
встал **над** ними: не «как найти текст», а «что мы вправе о нём утверждать».

---

## 1. Что было не так с постановкой

Детектор отвечал на вопрос «закончилась ли генерация» булевым значением и
числом `confidence`, полученным взвешенным голосованием DOM-признаков
(`calculateScore`, порог `0.6`). У этой постановки три независимых дефекта.

**Взвешенная сумма смешивает классы.** Пять согласных DOM-признаков — по-прежнему
утверждение о *проекции* ответа, а не о протоколе провайдера. Сумма делала их
неотличимыми от прямого терминального факта.

**Недоказанный результат неотличим от доказанного.** `{ success: true,
confidence: 0.85 }` и `{ success: true, confidence: 1 }` доходили до
потребителя одинаково: как текст, который можно использовать.

**Молчание наблюдателя читалось как молчание модели.** Сломанный хук,
отсоединённый content script и выгруженная вкладка дают ровно тот же
наблюдаемый признак, что и закончившая генерацию модель.

### 2.1. Типизированный результат

`COMMITTED`, `COMMITTED_TRUNCATED`, `SUSPECTED_COMPLETE`, `UNKNOWN`,
`OBSERVER_LOST`, `FAILED`, `CANCELLED`.

Пять осей оцениваются независимо: `identity`, `terminality`, `integrity`,
`semantic`, `observer`; каждая — `proven | suspected | unproven | contradicted`.
Технически терминальный run с `finish_reason=length` одновременно терминален и
содержательно неполон, поэтому одна булева «готовность» невыразима.

Неопределённость встроена в тип, а не приложена к нему. Ниже `COMMITTED`
обращение к `.text` бросает исключение; текст доступен только через
`readUncertainText(acknowledgement)`, и факт такого чтения записывается.
Свойство `text` неперечислимо, поэтому логирование и spread результата не
натыкаются на защиту — только намеренное чтение.

Заявка на commit, не подкреплённая осями, понижается **внутри контракта**, а не
на стороне вызывающего: недоказанная identity → `UNKNOWN`, недоказанная
terminality → `SUSPECTED_COMPLETE`, `BLIND` гарантия → `UNKNOWN`,
**опровергнутая integrity → `UNKNOWN`** (доказанная терминальность потока не
лечит повреждение того, что по нему пришло).

`unproven` на осях `integrity` и `semantic` намеренно **не** понижает: пока в
дереве нет независимого источника для reconciliation, эти оси недоказаны у
каждого run, и гейт на них не пропускал бы ничего. У `terminality` и `identity`
источники есть, поэтому там `unproven` понижает. Граница записана в коде рядом
с проверкой, а не только здесь.

### 2.2. Лестница доказательств

```
P0  семантический терминал провайдера   [DONE], message_stop, finish_reason
P1  завершение транспорта               поток генерации закрылся
P2  состояние приложения                собственный idle/streaming флаг страницы
P3  проекция DOM/UI                     Stop исчез, Regenerate появился, текст стабилен
P4  временная эвристика                 тишина, score, таймаут
```

Классы не складываются. Терминальность доказывает только P0; P1 — лишь там, где
доказан контракт «один поток = один ход». Согласие нескольких слабых сигналов не
повышает класс — это записано отдельным reason-кодом
`weak_agreement_does_not_promote_class`, чтобы сумму нельзя было ввести обратно
незаметно.

Один противоречащий факт запрещает commit при любом объёме согласия:
`stream_open`, `generation_active`, `stop_button_visible`, `text_shrunk`,
`identity_mismatch`, `observer_blind`.

Некоррелированный сигнал **отбрасывается**, а не учитывается с меньшим весом:
это свидетельство о другом run. Корреляция, установленная только причинным
порядком, честно помечается `causal_order` и опускает гарантию ниже строгой.

**Неоднозначность — не слабость.** Причинный порядок различает поток хода, пока
в окне run ровно один generation-запрос. При двух и более наблюдатель не может
сказать, какой поток породил текст на странице, и терминальный маркер чужого
потока доказал бы полноту не того ответа. Поэтому свидетельство помечается
`ambiguous` и **отбрасывается лестницей**, а не приписывается более вероятному
потоку. Побочный эффект честный: платформа, шлющая на том же endpoint
служебный запрос, теряет P0 и деградирует на DOM-путь — это видно в телеметрии
как `ambiguousCorrelation`.

### 2.3. Потолок гарантии

`STRICT → DEGRADED → HEURISTIC → BLIND` задаётся не числом голосов, а тем, какой
из каналов наблюдения жив: transport → `STRICT`, application → `DEGRADED`,
DOM → `HEURISTIC`. Потеря сильного наблюдателя **опускает потолок**, а не
убирает один голос. Ослепший DOM-наблюдатель отменяет доказательность тишины.

Наблюдатель считается обязанным что-то сообщать только пока предполагается
активная выдача. Замолчавший сенсор после дописанного ответа — нормальное
поведение, а не поломка.

### 2.4. Наблюдение транспорта

**Найденный по дороге дефект.** Main-world мост читал init из
`window.__HFM_INIT__`, куда content script пишет в *изолированном* мире, не
видимом мосту. Хук выходил на первой строке — на всех платформах, всё время.
Утверждение `answers-detection-alternativa.md` о том, что перехват `fetch`
«уже построен и работает», было неверным: инфраструктура была, наблюдений не
было. Init передаётся теперь на самом внедряемом элементе.

Мост сообщает жизненный цикл запроса, несущего ход: `request`, `start`,
`first_chunk`, `terminal_marker`, `end`, `error`, `unobservable`. Тело читается
через `response.clone()` — объект Response страницы не подменяется. Наружу
уходят только счётчики и маркеры; текст ответа из main world не выходит.

`provider-stream-semantics.js` — это контракт, а не эвристика: какие endpoint
несут ход, какие байты означают его конец, доказано ли «один поток = один ход».
`oneToOne` равен `false` у всех десяти провайдеров, пока не измерено, поэтому
закрытие потока входит в лестницу как подозрение (P1), а не как доказательство.
**Смена этого флага — результат калибровки, а не уборка кода.**

## 3. Что изменилось на боевом пути

`unified-answer-watcher.js` вычисляет вердикт лестницы на каждом такте:

1. **Veto.** Открытый поток генерации этого run или текст короче собственного
   максимума внутри одного хода блокируют commit, который сделали бы DOM-ветки.
   Ожидание — дешёвая ошибка, принятый недописанный ответ — дорогая.
2. **Ветка P0.** Терминальный маркер провайдера завершает run напрямую — но
   только после того, как renderer догнал producer. Терминальность относится к
   потоку, текст берётся со страницы; это разные компоненты.
3. **Типизация.** Каждый результат несёт `runProof`. DOM-only завершение — это
   `SUSPECTED_COMPLETE` под гарантией `HEURISTIC`: тот же зелёный, что и раньше,
   но уже отличимый от доказанного.

Контракт доходит до фонового потребителя: `buildResponseMeta` несёт `runResult`
в `responseMeta`, адаптеры кладут его в `meta.responseMeta`, и `AnswerEvidence`
в background читает именно его. `COMMITTED` там — самостоятельное терминальное
свидетельство (сильнейшее из имеющихся: оно уже потребовало доказанных identity
и terminality). `UNKNOWN / OBSERVER_LOST / FAILED / CANCELLED` не финализируются
с этого пути вовсе, с явной причиной `unproven_run_result_*`.

`unified-answer-pipeline.js` в финализации связывает решение с извлечённым
текстом: `structuralComplete` заполняет ось `semantic`, согласие снимков — ось
`integrity`. Структурно неполное извлечение даёт `COMMITTED_TRUNCATED`.

`PIPELINE_COMPLETE` несёт `resultType`, `resultGuarantee`, `evidenceClass`,
`terminalReason`. Все три первых ключа явно внесены в allowlist
`compactProofMetadata` — иначе их постигла бы судьба `submitMethod`.

## 4. Сознательно не сделано

**Граница зелёного не переехала.** Сегодня почти всё завершается по DOM, и
перевод всех DOM-завершений в `PARTIAL` был бы продуктовым изменением,
принимаемым по данным калибровки, а не по конструкции. `AnswerEvidence`
понижает до `PARTIAL` только `UNKNOWN / OBSERVER_LOST / FAILED / CANCELLED`.

**`oneToOne` не выставлен ни у одного провайдера** — см. 2.4.

**Application-канал (P2) не реализован.** Поиск internal app state по
поведенческой сигнатуре остаётся кандидатом; в witness set канал объявлен и
всегда `BLIND`, что честно опускает потолок, а не завышает его.

**`.text`-guard не обязывает фон.** Через границу процессов едет сериализованный
`runResult` (тип, гарантия, оси), а не объект с геттером: сообщение
`chrome.runtime` — это JSON. Ограничение в background выражено через
`AnswerEvidence`, а не через исключение при чтении. Полноценный guard за
границей потребовал бы восстанавливать контракт в фоне — это следующий шаг,
если понадобится.

**Reconciliation сети и DOM не выполняется.** Ось `integrity` заполняется
согласием снимков DOM между собой — это не независимый источник. Пока текст
собирается только из DOM, cross-channel сверять не с чем; она появляется вместе
с network-материализацией.

**Ревизии, phi-accrual, offline-oracle, event-sourced persistence** — не
входили в этот заход.

## 5. Что проверять дальше

1. **Живой прогон с включённым транспортом.** Метрика: доля run с
   `evidenceClass = P0` по платформам. Ноль на платформе означает, что её
   generation-паттерн в `PROVIDER_STREAM_SEMANTICS` не совпадает — это
   исправляется данными, а не догадкой.
2. **Частота veto `stream_open`.** Каждое срабатывание — предотвращённая ранняя
   финализация; это прямое измерение того самого дефекта, ради которого всё
   строилось.
3. **Совпадение P0 с текущим сигналом стабильности.** Систематически раньше и с
   той же финальной длиной — гипотеза A1 подтверждена, и тогда осмысленно
   ставить `oneToOne` по платформам.
4. **Доля `ambiguousCorrelation` по платформам.** Высокая означает, что
   generation-паттерн слишком широк и захватывает служебные запросы; это
   сужается данными, а не догадкой.
5. **Калибровка `SUSPECTED_COMPLETE`.** Если доля усечённых ответов среди них
   существенно выше, чем среди `COMMITTED`, разделение работает и границу
   зелёного можно двигать по данным.
