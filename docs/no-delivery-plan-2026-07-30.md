### 0.4. Дефект промпта, повлиявший на исходные ответы

Промпт для внешних моделей содержал остатки предыдущего задания: раздел C
требует цепочку до наблюдения «SUCCESS зафиксирован, текст продолжает
меняться», а «РАБОТА С КОДОМ» п. 5 говорит про «False success». Из трёх
ответов один (Z.ai) целиком отвечает на предыдущую задачу и к No delivery
отношения не имеет; у GPT раздел C2 уходит в ту же сторону. При следующем
прогоне раздел C должен формулироваться от текущего симптома.

## 1. Метод проверки и слепые зоны

### 1.1. Что проверено

Все утверждения ниже — чтение текущего кода с якорями `файл:строка`, если не
указано иное. Исполнением в этой итерации ничего не проверялось: разрыв

## 2. Восстановленная цепочка доставки

```
content: pipeline/fallback материализует текст
  → sendResult / chrome.runtime.sendMessage({type:'LLM_RESPONSE', meta})
background/message-router.js:
  :860  validateLifecycleSender      → sender_tab_mismatch
  :895  validateLifecycleCorrelation → missing_dispatch_id / dispatch_mismatch
  :3050 isTerminalRouterEntry        → response_ready_ignored_terminal (для LLM_RESPONSE_READY)
background/job-orchestrator.js:
  :8201 !accepted                    → ранний return, LLM_PARTIAL_RESPONSE как кандидат
  :8382 commitAcceptedAnswer         → entry.answer
  → sendMessageToResultsTab({type:'LLM_PARTIAL_RESPONSE'})
background/ui-broadcast.js:86        → tabs.sendMessage, при ошибке runtime-broadcast, при
                                       "no receiver" — только console.warn
results.js:
  :15897 case 'LLM_PARTIAL_RESPONSE'
  :15911 updateDebateModelCardOutput  → всегда
  :15930 if (autoMode || revealManualPing) updateLLMPanelOutput
         else storeResponseForManualMode                      ← панель не обновляется
  :16260 if (debateUpdate?.postTerminalRevision) return        ← панель не обновляется
  :16261 if (panel) { ... }                                    ← панели нет — тихий выход
  :19730 ensureDebateSession(activeSessionId)                  ← адресация по активной сессии
```

**Вывод.** Доставка проходит семь независимых сужений, и **пять из них
завершаются молча**: без телеметрии, без ошибки и без изменения состояния.
Сквозной квитанции доставки в цепочке нет — `ANSWER_CARD_RENDER_EVALUATED`
(`results.js:16215`) эмитится только внутри `updateLLMPanelOutput`, то есть
ровно в тех ветках, до которых дошли.

## 5. Классификация: это не один дефект

| Класс | Что происходит | Носители |
|---|---|---|
| **A. Отвержение на границе** | Сообщение не проходит guard identity | Qwen H2, N7; N6 — ложный след |
| **B. Терминальный отказ** | Запись уже терминальна, текст выброшен | Qwen H1, H1а, H3 |
| **C. Потеря в транспорте** | Сообщение отправлено, приёмника нет | N2, N3 |
| **D. Ошибка адресации** | Доставлено, но не в ту карточку | GPT H3, N5 |
| **E. Подавление отображения** | Доставлено и адресовано, но не отрисовано | **N1, N4**, N8, N9 |
| **F. Маскировка** | Пользователь видит зелёный статус поверх старого текста и не понимает, что ответа нет | GPT H4 |

Классы E и D дешевле всего проверить и починить, и именно они не были названы
ни одной внешней моделью. Класс A по итогам проверки оказался слабее, чем
считает GPT.

## 6. Оценка решений, предложенных моделями

| Решение | Оценка | Позиция |
|---|---|---|
| **GPT:** передать `dispatchMeta` в `sendResult` Grok | Правильная правка, неправильное обоснование | **Принять**, но переформулировать: она не восстанавливает доставку (её обеспечивает второе сообщение), а устраняет ложный сигнал `LIFECYCLE_CORRELATION_REJECTED`, отравляющий диагностику. Расширить: не терять `payload.meta` |
| **GPT:** ACK-телеметрия в `sendResult` | Ценно | **Принять и обобщить** на все адаптеры и на весь путь, а не только на producer→router |
| **Qwen:** доставлять текст `LLM_RESPONSE_READY` при терминальной записи через `allowTerminalUpgrade` | Верное направление, опасная формулировка | **Принять с ограничением.** Разрешать только для терминальных **отказов** (`ERROR`, `EXTRACT_FAILED`, `STREAM_TIMEOUT`, `NO_SEND`, `UNRESPONSIVE`), никогда — поверх залоченного SUCCESS. Иначе это прямой откат защиты, восстановленной планом false-success. Сам Qwen назвал риск (stale-ответ при неотправленном запросе) и предложил проверку `entry.promptSubmittedAt` — её сделать обязательной |
| **Qwen:** расширить `answerTextLength` в телеметрии отказа | Ценно, минимально | **Принять** |
| **Z.ai:** `LATE_RESPONSE_DROPPED_TERMINAL` | Дублирует уже существующее `ANSWER_DELIVERY_REJECTED` (`message-router.js:3052`) | **Отклонить** как новое событие; вместо этого дополнить существующее полями |
| **Z.ai:** ужесточить `content_mutation_stable` | Вне предмета и уже сделано | **Отклонить** — реализовано коммитом `460fce8` |

Ни одно из предложенных решений не касается классов C, D и E, то есть той
части цепочки, где потери происходят молча.

## 7. План реализации

### Этап 0 — база и сквозная квитанция

```bash
git checkout codex/no-delivery-telemetry
git tag v-before-no-delivery-repair
git checkout -b fix/no-delivery-chain
npx jest 2>&1 | tail -5
```

**0.1. Сквозная квитанция доставки.** Ввести один идентификатор
`deliveryId` (генерируется в `handleLLMResponse` при отправке
`LLM_PARTIAL_RESPONSE`) и три обязательных события с ним:
`ANSWER_DELIVERY_SENT` (background, `ui-broadcast.js:86`),
`ANSWER_DELIVERY_RECEIVED` (`results.js:15897`),
`ANSWER_CARD_RENDER_EVALUATED` (существует, `results.js:16215` — добавить
`deliveryId`).
Отсутствие второго события при наличии первого = класс C; отсутствие третьего
при наличии второго = класс D или E.
**Почему безопасно до установления причины:** ни одно решение не меняется,
добавляются поля и два события. Текст ответа в телеметрию не попадает.
**Приёмка:** `tests/answer-delivery-receipt.test.js` — полный путь даёт три
события с одним `deliveryId`; при закрытом results-табе — только первое.

### Этап 1 — молчаливое подавление отображения (P0)

Самый дешёвый и самый вероятный класс. Ни одна внешняя модель его не назвала.

**1.1. Убрать регресс `postTerminalRevision`**
- `results.js:16259-16260`
- Сейчас: `const debateUpdate = updateDebateModelCardOutput(...); if (debateUpdate?.postTerminalRevision) return debateUpdate;`
- Стало: не выходить досрочно. Панель обновлять всегда, но при
  `postTerminalRevision` — в отдельный блок ревизии с той же меткой, что и в
  ленте, не заменяя основной текст.
- **Зачем:** N4. Правка, внесённая планом false-success (`7168285`), сделала
  пост-терминальную ревизию невидимой в панели модели.
- **Приёмка:** `tests/results-post-terminal-render.test.js` дополнить: после
  терминала и ревизии панель содержит и исходный ответ, и блок ревизии.
- **Что станет хуже:** в панели появляется второй блок текста; вёрстка панели
  должна это выдержать.
- **Откат:** возврат раннего `return`.

**1.2. Ручной режим не должен скрывать полученный ответ**
- `results.js:15930-15940`
- Решение по существу: `autoMode` управляет **автоматической отправкой
  следующего шага**, а не видимостью уже полученного ответа. Полученный текст
  рендерить всегда; в ручном режиме — с явной меткой «ожидает подтверждения».
- Минимальный вариант, если менять семантику нельзя: оставить
  `pendingResponses`, но показывать в карточке явное состояние «ответ получен,
  нажмите Get Answers», а не пустоту.
- **Зачем:** N1. Сейчас в ручном режиме нормальный ответ выглядит как полное
  отсутствие доставки.
- **Приёмка:** `tests/results-manual-mode-delivery.test.js` — при
  `autoMode=false` приходит `LLM_PARTIAL_RESPONSE`; панель не пуста.
- **Что станет хуже:** пользователи ручного режима увидят текст раньше, чем
  нажали кнопку. Это и есть цель; но если режим используется как «не
  показывать до проверки» — потребуется отдельный флаг.
- **Решение противоречия:** если продукт настаивает на скрытии, тогда п. 1.2
  сводится к минимальному варианту (метка вместо пустоты). Оба варианта
  одновременно не принимать.
- **Откат:** тривиален.

**1.3. Телеметрия на тихих ветках**
- `results.js:19729` (пустой после санитайза), `:16261` (нет панели),
  `:16266-16268` и `:19735` (схлопывание по хэшу)

## 9. Чего не делать

- **Не разрешать доставку поверх залоченного SUCCESS.** Формулировка Qwen
  «доставить в карточку лучше, чем потерять» верна для терминального отказа и
  неверна для успеха: это откат защиты, восстановленной в `7168285`.
- **Не добавлять новое событие вместо расширения `ANSWER_DELIVERY_REJECTED`.**
- **Не чинить Grok как «ведущую причину».** Проверено: ответ доходит вторым
  сообщением; правка нужна ради диагностики, а не доставки.
- **Не трогать `content_mutation_stable`** — уже сделано в другом плане.

`0.1 → 1.1 → 1.2 → 1.3 → 2.1 → 2.2 → 1.4 → 3.1 → 3.2 → 4.1 → 4.2 → 5.1 → 5.2`
