# D6. Карта состояния, правила и решения

## Статус и назначение

Нормативный документ для канонического дела Disput, карты состояния, rule engine, окна прогресса и решений модератора. UI карты — проекция этих данных, а не отдельный источник истины.

## 1. Один источник истины

Запуск имеет два связанных, но разных представления:

1. `DebateRunStore` хранит фактический ход исполнения: этапы, события, решения, оценки правил, окно прогресса и технический статус.
2. `DebateCaseStore` хранит содержательное дело: claims, objections, evidence, revisions, dissent, limitations, связи, provenance и snapshots.

`DebateStateMap.project()` строит только читаемую проекцию. Изменение HTML карты не меняет дело. Любое содержательное действие человека проходит через типизированную команду `DebateCaseStore` и попадает в журнал.

## 2. Жизненный цикл артефакта

1. Ответ модели сохраняется как source event.
2. Checkpoint предлагает `StateDelta`.
3. Delta проходит схему, проверку ссылок и confidence gate.
4. Принятые операции атомарно применяются к делу.
5. Создаётся snapshot и diff.
6. Карта перестраивается из нового состояния.

Модель не закрывает спор и не управляет pipeline прямым self-report. Закрытие, reopening и принятие ограничения являются явными действиями runtime или человека.

Checkpoint и промежуточная фильтрация не являются отдельной ролью или
отдельным участником. Их выполняет тот же synthesizer, который создаёт
финальный ответ. Поэтому карта показывает один выбранный model identity для
всех synthesis-related service stages; независимый auditor появляется только
в отдельном audit-stage и не меняет карту напрямую.

## 3. Страницы карты

### Структура

Показывает дело как рабочий реестр: позиции, предположения и критерии; objections, contradictions, dissent и ограничения; evidence; revisions; оси проверки; элементы, требующие внимания. Карточка открывает drawer со связями, provenance, историей и допустимыми действиями человека.

### Graf

Показывает те же данные как сеть причинных связей. Узлы не дублируют состояние: идентификатор карточки совпадает с идентификатором артефакта, линии строятся из `targetId` и типизированных links.

### История

Показывает четыре независимые линии наблюдения:

- оценки и срабатывания правил текущего запуска;
- окно содержательного прогресса;
- полезность правил по завершённым запускам;
- диагностические `ModelSignal`, не влияющие на исполнение.

## 4. Правило pipeline

Правило является экземпляром конфигурации профиля:

```text
ruleId + triggerId + parameters + action + role
+ priority + cost + cooldown + maxExecutions + mode
```

`triggerId` определяет наблюдаемое условие. `parameters` уточняют его, например допустимые evidence tiers, severity или максимальное число кандидатов. `action` описывает следующий проверяемый вклад. `priority` и `cost` участвуют в выборе. `cooldown` и `maxExecutions` ограничивают циклы.

Результат оценки всегда объясним:

- `fired` — условие выполнено и действие допустимо;
- `suppressed / condition_not_met` — условие не выполнено;
- `suppressed / rule_disabled` — правило выключено;
- `suppressed / cooldown_active` — действует cooldown;
- `suppressed / execution_ceiling` — достигнут лимит повторов.

## 5. Control и shadow

FreeTalk использует `ruleMode: control`: выбранное правило может поставить действие в очередь.

Duel, Triad и Multi используют `ruleMode: shadow`: после общего checkpoint правила оцениваются и журналируются, но порядок фиксированного протокола не меняется. Перевод конкретного правила из shadow в control допустим только после данных о его точности, полезности и ложных срабатываниях.

## 6. Выбор следующего действия FreeTalk

1. Карта пересчитывается после checkpoint.
2. Все правила профиля оцениваются независимо.
3. Дубликаты active/queued действий отбрасываются.
4. Отбрасываются действия за пределами cooldown, execution ceiling и доступного бюджета с учётом резерва финализации.
5. Utility повышается для blockers, disputed facts и uncertainty; стоимость понижает utility.
6. В параллельный batch не попадают конфликтующие действия с одной целью или ролью.
7. Детерминированная маршрутизация ранжирует модели по авторству цели,
   требованию независимости и явно известной доступности инструмента. Она не
   оценивает «интеллект», качество, цену или скорость модели. Если обязательный
   инструмент отсутствует у всего выбранного состава, запуск профильной задачи
   блокируется, а не продолжается под видом degraded-исследования.
8. После ответа checkpoint определяет, изменилась ли карта; только это считается содержательным прогрессом.

## 7. Окно прогресса и fallback

Профиль задаёт `windowSize`, `minChangedSteps` и `fallback`. В окно записывается результат каждого выполненного действия: изменило оно дело или нет. Стагнация возникает, когда заполненное окно содержит меньше `minChangedSteps` изменений либо карта несколько циклов имеет один fingerprint.

Fallback не скрыт в runner. Создаётся `DecisionRequest` с выбором:

- собрать итог;
- разрешить ровно один дополнительный целевой шаг;
- остановить запуск.

Дополнительный шаг создаётся как отдельное действие `HUMAN_CONTINUE`; он не отключает защиту от будущей стагнации.

## 8. DecisionRequest

Любая содержательная развилка имеет:

- `requestId`, run/stage/subject;
- ясный вопрос и причину;
- режим `auto`, `assisted` или `manual`;
- от двух до пяти вариантов;
- рекомендуемый и безопасный default;
- для каждого варианта — `effect` и payload.

Основные effects: выполнить, отложить, отклонить, принять как ограничение, перейти к итогу, разрешить один шаг, остановить запуск. Выбор создаёт `DECISION_RESOLVED`, сохраняется как human decision и при необходимости изменяет целевой артефакт.

Здесь `DecisionRequest.mode: auto` — внутреннее правило выбора заранее
объявленного безопасного default, а не переключатель `debate-auto-toggle` и не
выбор модели. В `assisted` карта показывает рекомендацию, но ждёт человека. В
`manual` runtime также ждёт явного выбора и не подменяет его timeout-решением.

## 9. ModelSignal

FreeTalk может попросить модель добавить короткий блок `<disput-signal>`. Runtime удаляет его из видимого ответа, валидирует и пишет в диагностику. Сигнал:

- не создаёт артефакт;
- не меняет readiness;
- не запускает правило;
- не закрывает objection;
- не считается progress.

До отдельной калибровки допустим только режим `shadow`.

## 10. Межзапусковая аналитика

`DebateRuleHistory` хранит ограниченную историю завершённых запусков и агрегирует по правилу:

- число оценок;
- fired/suppressed;
- fire rate;
- число выполненных действий;
- долю действий, после которых изменилась карта.

Эти числа помогают менять профиль, но сами не перенастраивают production-правила. Автоматическое обучение на собственной метрике пока запрещено.

## 11. Инварианты

- Карта всегда восстанавливается из canonical state.
- Одно решение имеет один `requestId` и один итог.
- Rule trace сохраняет не только fired, но и причину suppression.
- Shadow rule никогда не меняет flow.
- ModelSignal никогда не меняет flow.
- Progress определяется `StateDelta`, а не длиной или уверенностью ответа.
- Бюджет финализации нельзя расходовать на очередное действие.
- Dissent и accepted limitations не исчезают из synthesis.
