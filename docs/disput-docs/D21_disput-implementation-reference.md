# D21. Справочник фактической реализации Disput

## Назначение

Этот документ связывает смысловые контракты D1–D11 с тем, что реально есть в
расширении: модулями, хранилищами, элементами интерфейса, командами и тестами.
Он нужен для быстрого восстановления контекста в новой беседе. Это не второй
архитектурный контракт: точные значения и допустимость операции определяют код
и тесты, а D2–D11 определяют смысл и правила.

## 1. Два слоя работы

Disput одновременно ведёт:

1. **Исполнение** — открывает вкладки моделей, отправляет запросы, ждёт ответы,
   повторяет неудачные попытки, проходит раунды и завершает pipeline.
2. **Содержательное дело** — сохраняет позиции, возражения, доказательства,
   связи, решения человека и историю изменения понимания задачи.

`DebateRunStore` отвечает за первый слой. `DebateCaseStore` отвечает за второй.
`DebateStateMap` только показывает дело. Telemetry показывает здоровье исполнения.
Смешивать эти три представления нельзя: успешная доставка ответа не означает,
что содержательное дело продвинулось.

## 3. Pipeline и prompt

Профиль задаёт роли, стадии, правила, progress policy и ограничения. Выбранные
модели — параметры запуска, а не новая схема pipeline. До открытия вкладок
компилируется неизменяемый `DebateExecutionPlan`; изменения select после этого
не должны незаметно менять текущий run.

`debate-length-select` является источником ограничения длины ответа для
поддерживающих его stage prompts. Значение должно попасть в контекст compiler;
prompt не должен обещать «без ограничения», если профиль или select задали
лимит. Prompt выбирается по `Task + Stage + Action`, а не по имени pipeline.

Для topology `free_talk` интерфейс показывает `free-talk-budget-select` со
значениями `5`, `10`, `20`, `infinite`; значение по умолчанию — `10`. При
старте оно преобразуется в `resourceBudget { used: 0, limit, reserved: 1 }`.
`infinite` преобразуется в `limit: null`. Планировщик допускает обычное действие
только когда `used + action.cost <= limit - reserved`; успешно завершённое
действие увеличивает `used` на свой `cost`. Если pending-действия остались, но
не помещаются в доступный бюджет, runner завершает action-loop и при выбранном
Synthesizer переходит к финальному synthesis, затем
фиксирует `epistemicOutcome: budget_limited`. Round control для topology
`free_talk` скрыт; он не является вторым ограничителем этого запуска.

Синтезатор — одна выбранная служебная роль. В FreeTalk он также выполняет
checkpoint и фильтрацию, если профиль не объявил отдельный service role.
Extractor не является самостоятельным участником: старое понятие извлечения
не должно выбирать вторую модель; сохранённое legacy-поле `extractor`
игнорируется и не может скрыто назначить Synthesizer. Независимый Auditor появляется только как
явно выбранная модель audit-stage и не заменяет синтезатор. Первый участник
не подставляется ни для одной служебной роли.

`debate-synthesizer-select` содержит только `None` и конкретные модели.
`Auto` для синтезатора отсутствует, литерал `auto` из старых данных
нормализуется в `None`, а compiler и topology runners не подставляют первого
участника. При `None` compiler не создаёт `final:synthesis`; fixed topology
завершается последней содержательной стадией. FreeTalk MVP без Synthesizer
завершается после blind positions, потому что trigger-loop пока зависит от
checkpoint этой же модели.

`debate-auditor-select` также содержит только `None` и конкретные модели.
Auditor должен отличаться от Synthesizer и запускается только после
существующего синтеза. Легаси-значение `auditor: auto` нормализуется в `None`.
Если выбранный Synthesizer становится недоступен, runtime не выбирает ему
замену: `continue` завершает обсуждение без synthesis, а `retry` повторяет
запрос той же модели.

## 4. Что такое полное дело

Полное дело — это восстанавливаемый JSON `DebateCase`, а не картинка карты и
не HTML ленты. В нём находятся:

- идентичность дела, schema/version и timestamps;
- `TaskContract`, ProblemSpec, профиль и участники;
- исходные события ответов с устойчивыми `turnId`/sequence;
- артефакты claims, objections, evidence, assumptions, contradictions,
  revisions, open questions, criteria, dissent, conclusions и audit;
- provenance каждого артефакта: источник, stage/participant, correlation и
  confidence;
- принятые действия, решения человека, technical status и epistemic outcome;
- append-only `changes`, `snapshots` и accepted correlations.

Экспорт **карты** — это компактная детерминированная проекция для просмотра.
Он не обязан содержать исходные события и не восстанавливает дело. Экспорт
**дела** можно импортировать обратно после миграции и проверки ссылок. Импорт не
запускает pipeline и не изменяет уже выполняющийся run.

## 5. Действия карты и drawer

В блоке карты есть две страницы одного дела:

- **Структура** — реестр артефактов, статусов, evidence gaps, критериев и
  attention points;
- **Graf** — связи между теми же ID, построенные по `targetId` и typed links;
- **History** — rule trace, progress window, rule history и model signals.

Drawer показывает статус, человеческие действия, связи, переход к исходному
ответу и свёрнутый System Information. Действия человека проходят через
`DebateCaseStore`, а не через изменение DOM: подтвердить закрытие, оставить
открытым, запросить evidence и назначить действие/связь.

Связь, созданная человеком из drawer, помечается provenance
`state_map_drawer` и может быть удалена крестиком и в drawer, и на карточке
карты. Удаление — это `DELETE_ARTIFACT`; оно сохраняется как change/snapshot и
не разрешается, если у артефакта есть зависимые элементы. Связи, пришедшие из
модельных данных, таким способом не удаляются.

## 6. Экранные команды

| Команда | Смысл |
|---|---|
| Export карты | выгрузить текущую read-only projection |
| Case | выгрузить полное восстанавливаемое дело |
| Import | проверить JSON дела, мигрировать при необходимости и сделать его активным |
| Delete | удалить выбранное сохранённое дело из CaseStore |
| Profiles | выбрать, применить, проверить, скопировать, сохранить, импортировать и экспортировать профиль |

Для `Specialized profile` выбор карточки открывает Profiles. Команда
**Применить** привязывает выбранный профиль к активному pipeline; простое
переключение строки профиля ничего не меняет. `Research` проверяет требование
`web_research` до dispatch и не запускается на неподдерживаемом составе моделей.

`Actions: 5/10/20/∞` — не команда и не требуемое число запросов, а лимит
бюджетных единиц FreeTalk. Переключатель `Auto` задаёт только темп: включён —
раунды идут без пауз и кнопка запуска становится Pause; выключен — после
каждого раунда ожидание и кнопка запуска продолжает следующий раунд. Он не
меняет бюджет и не выбирает модели. Допуск конкретного действия без подтверждения задают
`ActionContract.mode` и `profile.policies.mode`; `ask-human` создаёт
`DecisionRequest` до исполнения.

Case и Import не дублируют друг друга: Case создаёт файл, Import принимает
такой файл обратно. Кнопки карты не запускают и не меняют pipeline.

## 7. Состояния и ошибки

Run health и epistemic outcome независимы. Pipeline может завершиться с
`partial_success` или `degraded_success`, а дело при этом остаться полезным.
Содержательный прогресс определяется принятым `StateDelta`, а не длиной ответа,
уверенностью модели или наличием сигнала. `ModelSignal` — только диагностика;
он не закрывает objection и не запускает правило.

Старый event, duplicate correlation, orphan target, неверная schema или
невалидная ссылка отклоняются и попадают в диагностику. Ошибка одного
участника требует явного решения продолжить сокращённым составом или остановить
run; тихое продолжение запрещено.

## 8. Проверки, которые должны оставаться зелёными

Ключевые гарантии покрывают application/runtime, case store, protocols, prompt
compiler/runtime, profiles, state-map view, exports и telemetry. Перед выпуском
нужно проверять полный Jest-набор, а не только UI-тесты карты. При изменении
контракта сначала меняется владелец в D1–D11, затем добавляется запись в
`docs/CHANGELOG.md`, а незавершённое оставляется в `reports/D19_disput-next-steps.md`.

## 9. Границы текущей реализации

Duel/Triad/Multi всё ещё имеют совместимые topology runners; полный единый
универсальный StageExecutor — дальнейшая миграция. FreeTalk уже использует
профильные правила, но автоматическое самообучение правил по собственной
статистике запрещено. Эти ограничения важны: наличие модуля или UI-кнопки не
означает, что соответствующий автоматический режим уже реализован.
