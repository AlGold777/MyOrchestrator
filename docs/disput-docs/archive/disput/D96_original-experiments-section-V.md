Дата: 2026-07-15. Основа: «Приоритизация развития Disput — версия Claude.md», раздел V.

**ЖАНР ЭТОГО ТЗ ДРУГОЙ.** Раздел V — не фичи, а эксперименты: каждый может НЕ дать улучшения. Поэтому каждая задача оформлена как гипотеза → дешёвая проба → решение (принять / итерировать / убрать). Правила для всех экспериментов:

1. **Флаг.** Каждый эксперимент живёт за флагом в едином конфиге: новый модуль `disput/debate-experiments.js` (`root.DebateExperiments`): `isEnabled(id)`, читает `chrome.storage.local` ключ `debateExperiments.v1` (объект `{ [id]: true }`), по умолчанию всё выключено. UI-переключатели — секция «Эксперименты» в настройках debate-страницы (найти существующую панель настроек по grep настроечного UI; если секции нет — простой список чекбоксов).
2. **Изоляция.** Код эксперимента не вплетается в базовые пути: точки входа — уже существующие swappable-места (deps, serviceRoles V9, prompt-контракты, benchmark-конфигурации). Выключенный флаг = поведение бинарно идентично (это проверяется тестом в каждой задаче).
3. **Измерение.** У каждого эксперимента заранее объявлены: метрика успеха, размер выборки (обычно 6–10 живых прогонов или fixtures), kill-критерий. Результаты — в `docs/experiments-log.md` (одна таблица: эксперимент / дата / выборка / результат / решение). Эксперимент без записанного результата считается проваленным.
4. **Удаление.** Если решение «убрать» — код эксперимента удаляется в той же итерации (не копится мёртвый флаг).

Исполнитель: LLM-агент среднего уровня. Общие правила — из ТЗ раздела I (рабочая папка `/Users/restart/Downloads/LLM_Sol-Fable`, без коммитов без запроса, IIFE-модули, deps-инъекция, зелёный `npx jest` после каждой задачи).

## X1. Семантические дубликаты: лексическая база → embeddings только при необходимости

**Гипотеза.** Автоматическая детекция повторов точнее и стабильнее checkpoint-триггера `REPEATED_POINT` (V4), который зависит от внимательности checkpoint-модели.

**Проба, этап 1 — БЕЗ embeddings (обязателен до этапа 2).**
1. Модуль `disput/debate-similarity.js`: `similarity(textA, textB)` — шинглы по 3 слова (нормализация: lowercase, без пунктуации/стоп-слов; русский+английский словарь стоп-слов константой) + коэффициент Жаккара; `findDuplicates(claims, threshold = 0.5)` → пары `{aId, bId, score}`. Чистые функции.
2. Применение (за флагом `semantic_duplicates`): после каждого `ingestCheckpoint` — прогон по активным claims registry; пары выше порога → пометка `duplicateOf` на более позднем claim + строка в RoundDelta (V3 `duplicateSignals`). НЕ удалять и НЕ мержить автоматически — только сигнал.
3. Измерение: на 6 прогонах (2 topology × 3 задачи) собрать пары; человек размечает каждую пару верно/ложно. Метрика: precision ≥ 0.7 при ≥ 3 найденных парах на run в среднем. Сравнить с тем, что поймал `REPEATED_POINT` на тех же прогонах (пересечение/дополнение).

**Проба, этап 2 — embeddings (только если этап 1 дал precision < 0.7 ИЛИ recall очевидно нищий — < половины повторов, замеченных человеком).**
4. В `api-fallback.js` — функция embeddings-вызова для одного провайдера (OpenAI `/v1/embeddings` или Gemini `embedContent`; выбрать по наличию ключа у пользователя, актуальные model ID проверить на момент реализации). Кэш векторов в памяти run (`Map` по claim id). Косинусная близость, порог подобрать на разметке этапа 1.
5. То же измерение. Дополнительный kill-критерий: latency embeddings-вызовов > 10% времени run ИЛИ требует ключа, которого нет у пользователя (эксперимент не должен добавлять обязательных зависимостей).

**Novelty/diversity scores (подзадача, только при успехе этапа 1/2).** `noveltyScore(wave)` = доля claims волны без дубликата среди прежних; `diversityScore(openings)` = средняя попарная НЕпохожесть стартовых позиций. Оба — в RoundDelta и W3-метрики, наблюдательные.

**Kill-критерий общий:** precision < 0.7 после этапа 2 → удалить, оставить только `REPEATED_POINT`. **Приёмка:** юнит-тесты similarity (пары с известными score, включая кириллицу); тест «флаг выключен = поведение идентично»; запись в experiments-log с разметкой.

## X2. Автопредложение topology / числа моделей / раундов по типу задачи

**Гипотеза.** Пользователь часто выбирает пресет неоптимально; система может предлагать лучше, опираясь на `problemSpec.taskType` (U4).

**Проба.**
1. Модуль `disput/debate-preset-advisor.js`: `advise({ problemSpec, availableModels })` → `{ presetName, models: N, rounds: N, reason }`. Таблица правил (константа, редактируемая): factual → Triad Verdict, 3 модели (нужен арбитр); red_team → Triad/Multi Red Team по числу моделей; decision → Duel Verdict, 3 раунда; analysis → Multi Verdict; creative → Multi, 1–2 волны (критика душит новизну — так и написать в reason); open-ended глубокая тема → Long. Правила — стартовая эвристика, честные `reason` обязательны.
2. UI (за флагом `preset_advisor`): при вводе темы на debate-странице — ненавязчивая строка под композером: «Совет: для этой задачи — {preset}, {N} моделей ({reason}) [Применить]». Никогда не менять выбор сам.
3. Измерение: счётчики показов/применений (локально, в тот же experiments-конфиг): применяемость < 20% за 30 показов → совет бесполезен или назойлив.
4. Обучение на истории прошлых runs НЕ делать (VI.19 приоритизации) — только статичная таблица.

**Kill-критерий:** применяемость < 20% ИЛИ пользователь жалуется на шум. **Приёмка:** юнит-тесты advise (по одному на строку таблицы + пустой spec → null); флаг выключен → строка не рендерится; счётчики пишутся.

## X3. Замена выпавшего участника с восстановлением контекста

**Гипотеза.** Вместо деградации (U3) выпавшего участника можно заменить свободной моделью, передав ей роль и отфильтрованный контекст, — и качество run сохранится.

**Проба (за флагом `participant_replacement`).**
1. Паттерн уже есть для синтезатора (`attemptedSynthesizers`-цикл) — обобщить для участника: в dropout-диалоге (U3) третья кнопка «Заменить на <модель>» (список: доступные модели не из run; если пусто — кнопки нет).
2. Восстановление контекста заменившей модели — НЕ полная история: промпт «вступления в run»: тема + ProblemSpec + роль выбывшего + последний round filter + последняя волна полностью + явное «Ты заменяешь выбывшего участника с волны N; его позиция до выбытия: <его последняя позиция>. Продолжай эту роль, можешь пересмотреть позицию с обоснованием». Собирается через U1 assemble (новый stageKind `replacement_onboarding`).
3. Замена фиксируется: `state.replacements.push({ dropped, replacement, atStage })`, trace-событие, отметка в ProcessAudit (V8) и в синтез-промпте («участник X с волны N — замена Y; непрерывность позиции не гарантирована»). `epistemicOutcome` НЕ деградирует автоматически (замена ≠ дыра), но signal пишется.
4. Ограничения: не больше 1 замены на run (второй dropout — обычный U3-путь); в Duel замена запрещена после открытий (слишком мала база контекста — сразу U3).
5. Измерение: 4–6 искусственных прогонов (выключить модель руками посреди run): доходит ли run до вердикта, упоминает ли вердикт замену корректно, деградировало ли качество на глаз (сравнить с тем же прогоном без замены). Плюс проверка отсутствия ссылок на «потерянный» контекст (замена не должна цитировать то, чего не видела).

**Kill-критерий:** заменившая модель систематически ломает согласованность (галлюцинирует прошлое run) — 2+ случая из 6. **Приёмка:** mock-тест цикла замены (диалог → onboarding-диспатч → продолжение волн); тест лимита «1 замена»; флаг выключен → кнопки нет; existing dropout-тесты U3 зелёные.

## X4. Параллельные синтезаторы

**Гипотеза.** Два независимых синтеза одного run расходятся достаточно часто, чтобы сравнение вскрывало ошибки синтезатора, которые сейчас невидимы.

**Проба (за флагом `parallel_synthesis`; только Triad/Multi с ≥ 3 участниками).**
1. Стадия `final:synthesis` диспатчится ДВУМ моделям параллельно (батч уже умеет: `promptsByModel` с одинаковым промптом; синтезатор №2 — из `resolveServiceRoles` V9, правило: следующий активный участник не-синтезатор и не-экстрактор). Оба ответа проходят T9-валидацию секций.
2. Сравнение — БЕЗ третьего LLM-вызова в первой итерации: рендер бок-о-бок в терминальном UI («Синтез A (модель)» / «Синтез B (модель)»), пользователь выбирает канонический (клик «Сделать основным» → `VERDICT_RECORDED` с выбранным, второй сохраняется как `alternativeVerdict`). До выбора канонического run в статусе awaiting_approval (механизм W5 review).
3. Аудит V7, если включён, гоняется только по выбранному.
4. Измерение: на 6 прогонах — как часто вердикты материально расходятся (человек: «совпадают / расходятся в деталях / противоречат»), и выбирал ли пользователь не-первый вариант. Ценность = доля прогонов с материальным расхождением ≥ 1/3 (иначе двойная цена синтеза не окупается).

**Kill-критерий:** расхождения < 1/3 выборки ИЛИ пользователь всегда берёт первый не глядя. **Приёмка:** mock-тест двойного диспатча и выбора канонического; тест: флаг выключен → одиночный синтез, бинарно идентично; conformance-сценарий «терминал» (U8) не ломается от alternativeVerdict.

## X5. Machine-readable JSON от участников

**Гипотеза.** Участники могут сами отдавать структурированный блок (claims/objections) в конце ответа, разгружая checkpoint-экстракцию (V1). Известный риск: веб-UI ломают строгие форматы (markdown-обёртки, «поправленные» кавычки, обрезка).

**Проба (за флагом `participant_json`; НЕ трогает registry, пока не доказана надёжность).**
1. К промптам волн (T2 STAGE_TASKS, все фазы кроме opening) — хвост: «В самом конце ответа добавь блок: \```json\n{"claims":[{"text":"...","type":"factual"}],"objections":[{"target":"<цитата 8+ слов>","text":"..."}]}\n\``` — одна строка на элемент, без комментариев внутри блока».
2. Парсер `disput/debate-participant-json.js`: `extract(text)` → `{ ok, data, reason }` — найти последний fenced json-блок; санация типичных поломок ДО JSON.parse: смарт-кавычки → прямые, trailing comma, обёртка в лишний markdown. Парсинг строгий после санации; никакой eval-подобной гибкости.
3. Этап A — только измерение (ничего не потребляет данные): на каждом ответе писать в `state.participantJsonStats = { attempted, parsed, failedByModel: {} }` + trace-событие при провале. 6–10 прогонов, все модели: parse-rate по моделям.
4. Этап B (только если общий parse-rate ≥ 85%): распарсенные claims/objections подаются в checkpoint-промпт как «само-отчёт участников» (подсказка экстрактору, НЕ прямая запись в registry — anchor-валидация остаётся единственными воротами). Сравнить V1-метрики (deltas applied/rejected) с/без подсказки на 4 прогонах.
5. JSON-блок вырезается из текста перед показом в UI-ленте и перед подачей ответа другим участникам (шум) — но сохраняется в raw-тексте события.

**Kill-критерий:** parse-rate < 85% на этапе A (риск подтверждён — удалить, записать per-model цифры: они пригодятся при будущем переходе на API-транспорт). **Приёмка:** юнит-тесты extract (валидный / смарт-кавычки / trailing comma / блок в середине текста → берётся последний / нет блока); тест вырезания блока из ленты; флаг выключен → промпты без хвоста.

## X6. Дешёвая модель для extraction и compression

**Гипотеза.** Checkpoint-экстракцию и round filter может выполнять дешёвая API-модель (gemini-flash / qwen-turbo / deepseek-chat) без потери качества дельт — снимая нагрузку с вкладки синтезатора и ускоряя run.

**Проба (за флагом `cheap_extractor`; требует V9 serviceRoles и актуализированных model ID в api-fallback.js).**
1. В `resolveServiceRoles` (V9) — поддержка значения `extractor: 'api:<LLM>'`: сервисные стадии с таким экстрактором идут через `runModelBatch({ useApiFallback: true, models: [<LLM>] })`, минуя вкладку (проверить, что `useApiFallback: true` действительно форсирует API-путь, а не только фолбэк — разведка в `runModelBatch`/`api-fallback.js`; если сейчас это только фолбэк при сбое вкладки — добавить режим `transport: 'api_only'` в контекст батча).
2. UI: в селекторе экстрактора (V9.2) — группа «через API (нужен ключ)»; пункт неактивен без сохранённого ключа провайдера.
3. Измерение — прямое сравнение V1-метрик: 4 прогона с обычным экстрактором vs 4 с дешёвым (те же задачи): parse-rate, applied/rejected, ручная оценка качества 10 случайных дельт (верна ли классификация, точен ли anchor). Плюс замер длительности сервисных стадий (W4 observability).
4. Compression (сжатие для T11-переполнений через дешёвую модель) — НЕ делать в этой пробе: по приоритизации (II.12) LLM-compression — последний резерв; отметить в experiments-log как возможное продолжение при успехе экстракции.

**Kill-критерий:** качество дельт заметно хуже (rejected-rate вырос > 1.5×) ИЛИ ручная оценка нашла системные ошибки классификации. **Приёмка:** юнит-тест resolveServiceRoles c `api:`-значением; mock-тест транспорта (checkpoint-батч ушёл с api-only контекстом); без ключа пункт disabled; experiments-log с табличкой сравнения.

## X7. Web search как verification tool (через Perplexity)

**Гипотеза.** Для factual-задач claims с `verificationStatus: source_provided` можно проверять реальным веб-поиском, поднимая их до «проверен» / опуская до «источники противоречат» — без интеграции внешних API, потому что Perplexity уже участник `LLM_TARGETS`.

**Проба (за флагом `web_verification`; требует W2 verificationStatus; только `taskType: factual` или `evidenceMode: required`).**
1. Стадия `final:verification` ПЕРЕД синтезом (компилятор: kind `EVIDENCE_VERIFICATION`; валидатор U5 — inputs: фильтры): исполнитель — Perplexity, если она среди доступных моделей (не обязана быть участником run; вкладка создаётся как для сервисной стадии). Нет Perplexity → STAGE_SKIPPED, reason `no_search_capable_model`.
2. Промпт (контракт `evidence_verification`): топ-K claims (K=5, по типу factual с приведёнными источниками, из registry) → «Для каждого утверждения: найди независимые источники, вердикт: подтверждено / опровергнуто / источники противоречат / не нашёл. Формат: нумерованный список, по вердикту и 1–2 ссылки на пункт».
3. Результат — ЧЕЛОВЕКУ, не в registry напрямую: панель «Проверка фактов» с вердиктами и ссылками; человек кликом подтверждает → W2 human-оп ставит `source_verified`/`disputed_sources` (правило «verified ставит только человек» НЕ нарушается — Perplexity лишь готовит материал). Синтез-промпт получает панель как вход с пометкой «результаты автоматического поиска, не подтверждены человеком, взвешивай соответственно» — если человек не успел подтвердить.
4. Код execution и полноценный RAG — НЕ в этой пробе (для браузерного расширения это отдельный проект; зафиксировать в experiments-log).
5. Измерение: 4 factual-прогона: сколько из K claims получили полезный вердикт (человек: «помогло / шум»), сколько времени добавила стадия.

**Kill-критерий:** полезность < половины вердиктов ИЛИ стадия добавляет > 5 минут на run. **Приёмка:** компиляция плана со стадией проходит валидатор; skip без Perplexity покрыт тестом; mock-тест «человек подтвердил → verificationStatus обновился»; синтез-промпт содержит пометку о неподтверждённости.

## X8. Пользовательский feedback loop по качеству синтеза

**Гипотеза.** Даже грубая оценка пользователем накапливается в полезный сигнал: какие пресеты/синтезаторы стабильно дают слабые вердикты.

**Проба (за флагом `synthesis_feedback`; самый дешёвый эксперимент — делать первым).**
1. Под финальным вердиктом — строка: «Оценка синтеза: [полезен] [частично] [бесполезен]» + необязательное поле «что не так» (3 пресета быстрых ответов: «потерял важное», «вода», «не ответил на вопрос» + свой текст).
2. Хранение: `chrome.storage.local` ключ `debateSynthesisFeedback.v1` — массив `{ runId, presetName, topology, synthesizer, taskType, rating, tags, comment, at }` (кап 200 записей, FIFO). НИКУДА не отправляется — локальная аналитика.
3. Просмотр: в telemetry-view (W4) — таблица агрегатов: средняя оценка по пресету / синтезатору / taskType (при ≥ 5 оценках в ячейке, иначе «мало данных»).
4. Обучение выбора протокола на этих данных НЕ делать (VI.19/VI.23 приоритизации) — только показ человеку. Единственная автоматика: preset-advisor (X2), если включён, добавляет к reason «средняя оценка этого пресета у вас: N/3» при ≥ 5 оценках.
5. Измерение самого эксперимента: доля run с оставленной оценкой за 3 недели; < 15% → виджет не работает (переместить/упростить или убрать).

**Kill-критерий:** участие < 15% после одной итерации улучшения виджета. **Приёмка:** тест записи/капа хранилища; тест агрегатов (порог 5 оценок); флаг выключен → строки нет; оценка не блокирует терминальные действия run.
