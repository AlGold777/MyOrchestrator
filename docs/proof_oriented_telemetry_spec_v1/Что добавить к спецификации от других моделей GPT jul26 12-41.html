1. Авторизация producer → eventType → layer

Claude формулирует полезное правило: компонент не должен писать события чужого слоя. В текущей спецификации допустимые слои указаны в таблице компонентов, но это ещё не машиночитаемый контракт.

Добавить реестр:

{
  "eventType": "COMPLETION_HYPOTHESIS_EVALUATED",
  "requiredLayer": "inference",
  "allowedProducers": [
    "completion-inference-engine"
  ]
}

Новый инвариант:

S21 Producer authorization: producer.component, eventType и layer должны соответствовать Event Type Registry.

Validator должен отклонять, например, FINALIZATION_POLICY_EVALUATED, записанный DOM-adapter’ом.

При этом примеры сейчас местами используют универсальный:

"producer": {
  "component": "telemetry-core"
}

После введения S21 их нужно заменить реальными producer-компонентами.

2. Явное закрытие окна ожидания сигнала

Claude предлагает ABSENCE_CONFIRMED. Сама идея правильная, но универсальное название опасно: отсутствие события нельзя подтверждать без описания окна и качества наблюдений.

Лучше добавить:

EXPECTED_SIGNAL_WINDOW_CLOSED

Пример:

{
  "eventType": "EXPECTED_SIGNAL_WINDOW_CLOSED",
  "layer": "inference",
  "payload": {
    "expectedSignal": "first_generation_activity",
    "windowStartedMonoMs": 800,
    "windowEndedMonoMs": 15800,
    "windowDurationMs": 15000,
    "totalChecks": 12,
    "reliableChecks": 9,
    "observationCoveragePct": 82.4,
    "maximumObservationGapMs": 3100,
    "result": "not_observed",
    "confidence": "moderate"
  },
  "evidenceRefs": [
    "observation-frame-1",
    "observation-frame-12"
  ]
}

Допустимые результаты:

observed
not_observed
unobservable
window_interrupted

Это практически усилит отчёты:

  • request-not-sent;

  • generation-not-started;

  • true-completion;

  • forced-finalization.

3. Отдельная ось состояния post-terminal аудита

У Claude есть auditStatus. В текущей спецификации аудит представлен событием и derived-полями, но отдельной оси нет.

Добавить:

auditStatus:
  | "not_required"
  | "not_planned"
  | "planned"
  | "running"
  | "supports_decision"
  | "contradicts_decision"
  | "inconclusive"
  | "unavailable";

Это позволит без разбора payload сразу различать:

решение принято, аудит ещё идёт;
решение подтверждено;
обнаружена преждевременная финализация;
аудит технически невозможен.

4. Ограничение количества файлов в одном цикле эскалации

Claude правильно указал на риск гиперзапроса. Сейчас уже есть:

"maxEscalationDepth": 2

Но нет ограничения количества файлов на одном уровне.

Добавить:

{
  "antiLoopPolicy": {
    "maxEscalationDepth": 2,
    "maxRequiredReportsPerRound": 2,
    "maxOptionalReportsPerRound": 1,
    "doNotRequestAlreadyProvided": true,
    "doNotRequestAlreadyRequested": true,
    "requireNewQuestionToResolve": true,
    "overflowStrategy": "rank_and_defer"
  }
}

Ранжировать matched rules по:

  1. блокирует ли отсутствие файла causal verdict;

  2. способен ли файл различить конкурирующие причины;

  3. priority;

  4. число разрешаемых blockedConclusions;

  5. детерминированный ruleId как tie-breaker.

Невошедшие запросы хранить:

"deferredAdditionalReports": []

5. Машиночитаемый presetIndex в manifest

Из ответа Claude стоит взять саму идею индекса, но не eventTypeRange: события не образуют непрерывные диапазоны, а presets пересекаются.

Добавить:

{
  "presetIndex": [
    {
      "reportType": "truncation",
      "reportSchemaVersion": "1.0.0",
      "embeddedPath": "$.reports.truncation",
      "standaloneFilename": "truncation.json",
      "eventSelectionProfileId": "truncation-events@1",
      "derivedViewIds": [
        "candidate-lineage",
        "text-evolution",
        "completion-proof",
        "post-terminal-audit"
      ],
      "dependencyRuleSetId": "truncation@1"
    }
  ]
}

Это позволит инструменту или LLM быстро определить:

  • где находится нужный отчёт;

  • какие derived views ему соответствуют;

  • какой профиль событий использован;

  • какой набор escalation-правил применён.

6. Инвариант единственного актуального terminal decision

Z.ai предлагает:

1 dispatch = 1 decision

Это неправильно: возможны retry, recovery и DECISION_SUPERSEDED.

Но из идеи следует полезный более точный инвариант:

S22 Active terminal uniqueness: на одной export boundary у dispatch может быть несколько immutable decisions, но ровно одно terminal decision, которое не superseded.

Проверка:

count(
  terminal decisions
  minus superseded decisions
) <= 1

Для terminal dispatch:

count(active terminal decisions) == 1

7. Observer health score — только как derived metric

Claude предлагает числовой observerHealth: 0.0–1.0. Это удобно для сортировки и dashboards, но опасно как источник решения: одинаковый score может скрывать разные причины деградации.

Можно добавить:

{
  "observerHealth": {
    "score": 0.42,
    "algorithmVersion": "observer-health@1",
    "components": {
      "contentScriptAvailability": 1.0,
      "observationFreshness": 0.3,
      "schedulerAccess": 0.2,
      "selectorConfidence": 0.8,
      "documentContinuity": 0.5
    },
    "level": "degraded"
  }
}

Правило:

Completion policy MUST использовать первичные компоненты и reliability facts. Итоговый score используется только как диагностический derived indicator.

Что брать не следует

completionEvidenceTier: absent | weak | moderate | strong

Текущая шкала T0–T4 точнее: она различает provider terminal evidence и сильный UI transition.

terminalMode = forced_timeout | forced_error

Текущая модель лучше:

terminalMode = forced
terminationCause = extension_timeout

Она не смешивает способ финализации с причиной.

true_completion требует отсутствия любых post-terminal DOM mutations

Неверно. После завершения возможны нерелевантные DOM-мутации: кнопки, citations, layout, toolbar.

Нужно проверять:

  • hash принятого кандидата;

  • длину;

  • relevant mutations;

  • возобновление active-generation signals;

  • смену кандидата.

attachments без верхнего лимита

Не принимать. TTL не защищает от memory/storage pressure. Текущие per-attachment и total budgets нужны.

networkStatus == 200 как доказательство отправки

Для веб-интерфейсов LLM это ненадёжно и неуниверсально. Network telemetry может отсутствовать, запрос может идти через SSE/WebSocket, service worker или непрозрачный transport.

networkChunkLength > DOM length

Допустимо только при:

"capabilities": {
  "networkObservation": true,
  "networkContentCompleteness": "verified"
}

Иначе network length должна быть unknown, а не использоваться в правиле.

Укрупнение восьми отчётов в четыре технических файла

Не нужно. Это ухудшит пользовательский интерфейс. Внутренние evidence-домены могут быть общими, но пользовательские presets должны оставаться проблемно-ориентированными.

Итог

В спецификацию целесообразно добавить шесть обязательных изменений:

  1. S21 Producer authorization;

  2. EXPECTED_SIGNAL_WINDOW_CLOSED;

  3. ось auditStatus;

  4. maxRequiredReportsPerRound и ranking;

  5. машинный presetIndex;

  6. S22 Active terminal uniqueness.

observerHealth.score можно добавить как необязательный derived metric.

Остальные существенные идеи других моделей либо уже реализованы в текущей спецификации, либо являются упрощениями, которые снизят доказательность системы.
